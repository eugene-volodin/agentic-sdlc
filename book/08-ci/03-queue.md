## Merge queue

Но вот беда — когда у тебя в репозитории много пул-реквестов, каждый из них по отдельности может пройти все проверки, а вместе они сломают main. Допустим, один агент переименовал функцию `get_user` в `find_user` и поправил все места, где она вызывалась. А другой агент в это же время в своей ветке написал новый код, который вызывает `get_user` по старому имени. Каждый пул-реквест по отдельности зелёный, все проверки прошли, ведь в ветке второго агента функция ещё называется по-старому. Git смержит обе ветки без конфликта, потому что агенты правили разные файлы. Но вот main после этого будет сломан, ведь новый код вызывает функцию, которой больше нет.

В GitHub от этого защищает настройка «Require branches to be up to date before merging». С ней, прежде чем смержить пул-реквест, в его ветку нужно влить свежий main и прогнать CI ещё раз. Только вот когда пул-реквестов много, main успевает обновиться, пока идёт CI, и тебе снова нужно вливать main в свою ветку и снова ждать, пока пройдут проверки. И таких циклов может быть очень много.

Эту проблему решает **merge queue** — очередь пул-реквестов на merge, в GitLab она называется merge trains. Пул-реквест не мержат сразу, а ставят в очередь, и дальше GitHub всё делает сам:

::: steps
1. Ты ставишь первый пул-реквест в очередь. GitHub создаёт временную ветку, в которой к свежему main добавлен этот пул-реквест, и запускает на ней CI
2. Пока идёт CI, в очередь встаёт второй пул-реквест. Для него GitHub создаёт вторую временную ветку: main, первый пул-реквест и второй. Первая ветка никуда не девается, CI идёт на обеих сразу
3. Третий пул-реквест получает свою ветку с main и всеми тремя пул-реквестами, и так далее. Сколько веток проверяется одновременно, задаёшь в настройках очереди, а остальные пул-реквесты ждут, пока освободится место
4. Пул-реквесты мержатся в main строго по очереди: каждый — когда прошёл CI на его ветке. Ведь ветка второго уже включает первый, и в main попадает ровно тот код, который проверили
5. Если CI упал на ветке второго пул-реквеста, его убирают из очереди, а ветки всех, кто стоял за ним, пересобирают уже без него. Первого это не задевает
:::

В нашем примере пул-реквест второго агента проверится на ветке вместе с первым, CI упадёт, ведь функции `get_user` там уже нет, и пул-реквест уберут из очереди, не пустив в main. Агент, который ведёт этот пул-реквест, увидит упавшую проверку, вольёт свежий main и поправит вызов на `find_user`.

В GitLab merge trains устроены так же, только по умолчанию параллельно идут до 20 пайплайнов.

::: note cat
Merge queue в GitHub есть в любом публичном репозитории организации, а в приватных — только у организаций на тарифе Enterprise Cloud. Merge trains в GitLab есть начиная с тарифа Premium — [docs.github.com](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue), [docs.gitlab.com](https://docs.gitlab.com/ci/pipelines/merge_trains/)
:::

Нужна merge queue не всем. Если у тебя в репозитории несколько пул-реквестов в день или merge queue нет в твоём тарифе, хватит и настройки «Require branches to be up to date before merging». А вот когда пул-реквестов десятки и над одним репозиторием параллельно работают несколько агентов, без merge queue агенты будут по кругу вливать main в свои ветки и заново ждать CI.

::: note agent
Если я поставил пул-реквест в merge queue, а он там висит и не мержится, проверь, что workflow запускается не только на событие `pull_request`, но и на `merge_group`, иначе GitHub не запустит проверки на временной ветке. А если я мержу через API GitLab, запиши мне в `AGENTS.md`, что merge идёт с параметром `auto_merge=true`, иначе при обязательных merge trains GitLab вернёт ошибку 405
:::

```prompt who=cat title="Merge queue" note="-"
Подготовь наш CI к merge queue.
В GitHub: добавь событие merge_group в workflow с итоговой проверкой gate. В GitLab: проверь, что включены merged results pipelines — пайплайны, которые проверяют результат merge с main.
Напиши, что мне включить в настройках репозитория, чтобы пул-реквесты мержились только через merge queue, и сколько веток ты советуешь проверять одновременно для нашего числа пул-реквестов в день.
Покажи изменения до коммита.
```
