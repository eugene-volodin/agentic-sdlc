## Тестовые окружения: агенту можно всё

Локально, в dev-окружении, на стейдже и на превью-стендах я разрешаю агенту делать всё без моего разрешения: деплоить, разворачивать, менять секреты. Эти окружения для того и существуют, чтобы в них можно было ошибаться.

Только классификатор auto mode по умолчанию запрещает агенту записывать что-либо в хранилище секретов в любом окружении, даже в dev. А классификатор узнаёт прод только по названиям проектов, кластеров и серверов в командах агента: если в названии есть слово prod или production, он считает это продом, а про остальные твои окружения он ничего не знает. Поэтому классификатору стоит прямо написать, какие окружения у тебя продовые и требуют твоего разрешения, а в каких агенту можно менять всё без него. Пишется это обычным текстом в личных настройках `~/.claude/settings.json`, в блоке `autoMode`:

```json title="~/.claude/settings.json"
{
  "autoMode": {
    "environment": [
      "$defaults",
      "Protected deployment namespaces / environments: GCP project myapp-prod, kube context prod-eu"
    ],
    "allow": [
      "$defaults",
      "Deploying, migrating and changing secrets in dev, staging and preview (GCP projects myapp-dev, myapp-staging, myapp-pr-*) is allowed: they are isolated from production"
    ]
  }
}
```

Если ты скачал репозиторий, которому не доверяешь, то в его настройках, в файле `.claude/settings.json`, мог бы лежать такой же блок, который разрешает агенту всё подряд, и тогда агент смог бы тебе навредить. Поэтому классификатор читает блок `autoMode` только из твоих личных настроек и никогда — из настроек репозитория. Посмотреть, какие правила у классификатора сейчас действуют, можно командой `claude auto-mode config`, а команда `claude auto-mode critique` подскажет, где твои формулировки неоднозначны.

Обычно у проекта есть как минимум два окружения, prod и dev, и у каждого свой набор переменных, а локальное окружение разработчика должно совпадать с dev. Чтобы держать переменные в `.env` локально в актуальном состоянии, я рекомендую завести скрипт, который подключается к хранилищу секретов, будь то Vault, Google Secret Manager или AWS Secrets Manager, выкачивает все переменные dev-окружения и записывает их в локальный `.env`, удаляя прошлый. Так у разработчика всегда те же значения, что и в dev, и ему не нужно спрашивать у команды актуальные значения переменных. А когда кто-то добавляет новую переменную, он сразу заводит её во всех окружениях, и остальным, чтобы её получить, достаточно ещё раз запустить скрипт.

::: note cat
1Password делает менеджер паролей и умеет подставлять секреты только на время работы той программы, которую ты запускаешь через него. Но в его же документации сказано, что другие программы, которые работают под тем же пользователем, могут эти секреты прочитать, а значит, и агент тоже — [1password.dev](https://www.1password.dev/cli/secrets-environment-variables/)
:::

Агент прочитает всё, что лежит в `.env`, и auto mode ему это разрешит. Поэтому локально должны лежать только значения dev-окружения, а значения прода не должны попадать на компьютер разработчика никогда.

::: note cat
В апреле 2026 года основатель стартапа PocketOS рассказал, что агент Cursor на задаче на стейдже нашёл токен облачного хостинга Railway с правами на весь аккаунт в файле, который вообще не относился к задаче, и за 9 секунд удалил том с продакшн-базой и бэкапами на нём. Railway потом ответила, что базу удалось восстановить, и теперь удаление через API у них срабатывает только через 48 часов — [x.com/lifeofjer](https://x.com/lifeofjer/status/2048103471019434248), [blog.railway.com](https://blog.railway.com/p/your-ai-wants-to-nuke-your-database)
:::

Ну и раз даже dev-секреты теперь лежат рядом с кодом, то перед каждым пушем стоит проверять, не попал ли какой-нибудь из них в коммит. Для этого есть gitleaks — бесплатный инструмент, который ищет ключи и пароли в коде и истории git. Его можно запускать в git-хуке перед каждым пушем, и тогда коммит с ключом просто не уйдёт в удалённый репозиторий. В случае, если ключ всё-таки закоммитили и запушили, то удалить его из коммита мало, ведь он уже попал в историю git и в удалённый репозиторий, и кто-то мог успеть его скачать. В этом случае ключ нужно сразу заменить на новый (ротировать).

```prompt who=cat title="Свежий .env для dev" note="Подставь своё хранилище секретов"
Напиши скрипт, который берёт все переменные dev-окружения из нашего хранилища секретов ({{Vault, Google Secret Manager или другое}}) и пишет их в .env. Работать он должен только с dev-окружением, сначала писать во временный файл и заменять .env, только если всё скачалось. Значения в вывод не печатай.
Проверь, что .env не попадает в git.
Добавь git-хук, который перед пушем проверяет отправляемые коммиты gitleaks с флагом --redact, и проверь этот хук на фейковом ключе в отдельной ветке через git push --dry-run, а потом удали эту ветку.
```
