## CODEOWNERS и InnerSource

Раньше, если для твоей фичи нужно было что-то поменять в сервисе или модуле другой команды, ты заводил этой команде задачу и ждал, пока до неё дойдёт очередь в их бэклоге. А сейчас агент может сделать всё сам — и написать код в твоём домене, и поправить код в чужом. Такой подход называют **InnerSource** — это когда любой разработчик может контрибьютить в код другой команды, как в open source проект. И сейчас, с агентами, этот подход становится актуальным как никогда.

::: note cat
Термин «inner sourcing» придумал в 2000 году Тим О'Райли, основатель издательства O'Reilly Media. Сообщество InnerSource Commons объясняет его так — это когда практики open source переносят на разработку внутри компании. А в их руководстве о работе с ИИ прямо сказано, что сейчас InnerSource важнее, чем когда-либо — [innersourcecommons.org](https://innersourcecommons.org/documents/books/AdoptingInnerSource.pdf), [innersourcecommons.org](https://innersourcecommons.org/learn/learning-path/introduction/), [innersourcecommons.gitbook.io](https://innersourcecommons.gitbook.io/managing-innersource-projects/innersource-and-ai)
:::

При этом команда, которая владеет доменом, должна понимать, что приносят в её код другие, и соглашаться с этими изменениями. Поэтому первое, что я рекомендую, — это файл `CODEOWNERS`, где для каждой папки записано, какая команда за неё отвечает. Если ты в своей ветке затронул код чужого сервиса или модуля, на ревью автоматически позовут кого-то из этой команды, и без аппрува кого-то из них твой пул-реквест не смержится. Поставят ли они тебе аппрув не глядя или пойдут сами вычитывать каждую строчку кода — это уже их дело, но как минимум они будут в курсе про эти изменения.

Если в вашей компании InnerSource не принят, то самое время сейчас это поменять и начать внедрять его практики. Задача тут такая — твой агент должен писать код в домене другой команды ровно так, как будто его писал агент разработчика из этой команды. Для этого команде-владельцу нужно детально подготовить свой домен или свой репозиторий для агентов — положить `AGENTS.md` в папку модуля и добавить скиллы с правилами и знаниями этого модуля. Тогда твой агент сразу будет писать код правильно и ориентироваться в специфике их домена, а ребятам из соседней команды не придётся тратить много времени на ревью твоего кода.

В прошлой главе мы уже сделали аппрув владельцев кода обязательным для конфигов CI, тестов и линтеров, чтобы агент не мог ослабить проверки своего же кода. Теперь осталось дописать в тот же файл `CODEOWNERS` папки, которые ведут другие команды, и тогда обязательным станет аппрув и от владельцев этих доменов.

В GitHub и GitLab это настраивается по-разному:

- в GitHub ничего дополнительно включать не нужно: правило в ruleset ветки `main`, которое мы включили в прошлой главе, требует аппрув от владельцев всех файлов из `CODEOWNERS`, которые затронул пул-реквест. Достаточно аппрува любого человека из команды-владельца;
- в GitLab файл `CODEOWNERS` можно делить на секции — это заголовки в квадратных скобках вроде `[Payments]`, под которыми перечислены папки и их владельцы. Рядом с названием секции можно указать, сколько аппрувов от её владельцев нужно, например `[Payments][1]`, а обязательными они станут, если для защищённой ветки `main` включить аппрув владельцев кода.

::: note cat
В GitLab секции и обязательный аппрув владельцев кода есть только с тарифа Premium — [docs.gitlab.com](https://docs.gitlab.com/user/project/codeowners/reference/)
:::

```prompt who=cat title="Владельцы доменов" note="-"
Составь CODEOWNERS по папкам репозитория. Какая команда какой домен ведёт, спроси у меня.
Если пул-реквест меняет код домена, без аппрува хотя бы одного человека из команды-владельца он не должен мержиться. Конфиги CI, тестов, линтеров и сам CODEOWNERS оставь за командой, которая отвечает за CI.
Напиши, что для этого включить в настройках GitHub или GitLab, и покажи файл, прежде чем его записать.
```
